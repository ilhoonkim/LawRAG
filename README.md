# LawRAG

Python/FastAPI 백엔드와 React/Vite 프론트엔드로 구성한 로컬 법령 RAG 앱입니다. 왼쪽 메뉴는 **법령관리 / 채팅**으로 분리합니다. React 빌드 결과를 저장소에 포함하므로 실행만 할 때는 Node.js 설치 없이 Python 서버 하나로 사용할 수 있습니다.

## Windows 로컬 실행 및 업데이트

PowerShell에서 실행합니다. 기존 서버는 해당 창에서 `Ctrl+C`로 종료한 뒤 업데이트하세요.

```powershell
cd "C:\Users\김일훈\local_dev\LawRAG"
git pull --ff-only origin main
# 최초 설치 때만 가상환경을 생성합니다.
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (!(Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

브라우저에서 `http://127.0.0.1:8001`을 엽니다. 이미 설치했다면 pull 후 서버 재시작만으로 화면 변경이 반영됩니다. `.env`와 `data/`는 Git에서 제외하므로 로컬 키·수집 자료가 유지됩니다. Linux/macOS에서는 `.venv/bin/python`을 사용합니다.

Python 3.12, SQLite 확장 로드가 가능한 환경이 필요합니다. 수집 실행기는 단일 서버 프로세스를 전제로 합니다. 여러 `--workers`로 실행하지 마세요. 인증 없는 로컬 개발 앱이므로 공개 배포 전에는 인증·호출량 제한 등을 추가해야 합니다.

## 내부망에서 함께 사용하기 (로그인 없음)

서버를 실행할 PC의 기존 서버를 `Ctrl+C`로 종료한 뒤 프로젝트 폴더에서 실행합니다.

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m app.serve --lan
```

IPv4 인터페이스(`0.0.0.0`)의 8001 포트로 접속을 받으며 실행창에 접속 주소 후보를 표시합니다. `ipconfig`에서 **회사망에 연결된 Ethernet/Wi-Fi의 IPv4 주소**를 확인해 `http://해당IP:8001`을 공유하세요. 예를 들어 `192.168.0.10`이라면 `http://192.168.0.10:8001`입니다. `127.0.0.1`은 접속하는 사람 자신의 PC이며, `0.0.0.0`은 접속 주소가 아닙니다. 서버 PC와 실행 창이 켜져 있어야 합니다. 포트 변경은 `--port 8002`, 내 PC에서만 실행하려면 `--lan`을 빼면 됩니다.

Windows 방화벽에 해당 포트가 허용되지 않은 경우 **서버 PC의 관리자 PowerShell**에서 다음 명령을 한 번 실행합니다. 도메인/개인 네트워크의 같은 서브넷에만 허용하며 방화벽 전체를 끄지 않습니다.

```powershell
New-NetFirewallRule -DisplayName "LawRAG LAN 8001" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8001 -RemoteAddress LocalSubnet -Profile Domain,Private
```

서로 다른 사내 서브넷/VLAN에서도 사용할 때는 회사의 실제 내부망 대역을 `RemoteAddress`에 지정하고 망 사이 접근 정책을 확인해야 합니다. Windows 네트워크 프로필이 공용이면 위 규칙이 적용되지 않습니다. 포트를 바꿨다면 방화벽 포트도 맞추세요. 다른 PC에서 `Test-NetConnection 서버IPv4주소 -Port 8001`로 연결을 확인할 수 있습니다.

- **공유되는 것**: 법령 DB, 수집 상태·이력, 법령관리 기능, 서버의 API 설정. 현재 접속자는 모두 법령관리 기능도 사용할 수 있습니다.
- **분리되는 것**: 채팅 제목·질문·답변은 각 브라우저의 localStorage에만 보관합니다. 요청 시 해당 브라우저가 보낸 대화만 답변 문맥으로 사용하며, 다른 브라우저에 이력을 내려주는 서버 API는 없습니다.
- 로그인 대신 **브라우저 프로필 단위**로 구분합니다. 같은 PC·같은 프로필을 공유하면 이력도 공유하고, 다른 PC/브라우저에서는 자동 동기화되지 않습니다. 시크릿 창을 닫거나 사이트 데이터를 지우면 이력이 사라집니다.
- `http://127.0.0.1:8001`과 `http://내부IP:8001`은 저장소가 달라 이력이 별개로 보입니다. 기존 이력이 삭제된 것은 아니며 원래 주소로 접속하면 볼 수 있습니다. 주소/포트가 달라져도 같습니다.

## 환경 변수

`.env` 또는 프로세스 환경 변수로 설정합니다. 이미 주입된 값이 `.env`보다 우선하며 변경 후 서버를 재시작합니다. 키를 채팅이나 Git에 올리지 마세요.

| 변수 | 용도 / 기본값 |
|---|---|
| `LAW_API_OC` | 국가법령정보 공동활용 OC 식별값. 법령 및 사용하는 행정규칙 API 권한 필요 |
| `LLM_API_KEY` | OpenAI API 키. 미설정이면 기존 `OPENAI_API_KEY` 사용 |
| `LLM_BASE_URL` | `https://api.openai.com/v1`, embeddings/chat completions 호환 서버 |
| `EMBEDDING_MODEL` | `text-embedding-3-large` |
| `CHAT_MODEL` | `gpt-4.1` (채팅창의 초기 선택값) |
| `SEARCH_CANDIDATE_LIMIT` | 임계치 통과 검색 후보의 검토 수 `15`, 최대 `15`. 기존 `.env`가 20 이상이어도 상한 적용 |
| `SEARCH_THRESHOLD` | 기본 근거 임계치 `0.4`. 환경변수나 `.env`에 지정한 값이 있으면 우선 적용 |
| `SEARCH_FUSION` | 기본 순위 결합 `rrf`. 환경변수나 `.env`에 `weighted` 또는 `rrf`를 지정하면 우선 적용 |
| `REFERENCE_LIMIT` | 한 차례 관계 확장 시 추가 문서 최대 `40` (상한 80) |
| `CONTEXT_MAX_CHARS` | 최종 근거 본문 예산 `60000`자. 조 중간을 자르지 않고 초과 조는 누락 목록에 기록 |
| `DATA_DIR` | 기본 프로젝트 `data/` |

실제 연동에는 HTTPS `www.law.go.kr`, `api.openai.com` 접근이 필요합니다. 클라우드에서는 법령 API 연결이 제한되어 실제 연혁 건수와 본문 연동을 검증하지 못했습니다. 사용자 PC의 허용 IP 및 API 권한을 기준으로 별도 검증해야 합니다.

수집 중 AI 요청이 실패하면 `python -m app.check_ai`로 임베딩 연결을 확인합니다. 키의 존재와 설정 위치만 표시하며 키 값은 출력하지 않습니다. PowerShell 등 프로세스 환경변수는 `.env`보다 우선합니다. 이 진단은 짧은 문장 1개로 실제 임베딩 API를 호출하며 DB를 수정하지 않습니다. 연결에 성공해도 법령 본문의 길이·입력 형식 문제는 별도로 확인해야 합니다. 수집 화면과 이력에는 HTTP 상태 및 오류 종류를 표시합니다. 예를 들어 401은 인증, `429 / insufficient_quota`는 API 결제·잔액, `429 / rate_limit_exceeded`는 요청량 제한입니다. 과거 이력에 저장된 공통 오류 문구는 재시도 전까지 유지됩니다.

법령 다운로드와 AI 요청의 시간 초과·일시적 연결 오류, HTTP 408/409/425/429 및 재시도 가능한 5xx는 **최초 요청 후 최대 3회** 더 시도합니다. 기본 대기는 약 2·4·8초이며 서버의 `Retry-After`는 최대 60초까지 반영합니다. 이 자동 재시도 중에는 이미 성공한 임베딩 배치를 다시 보내지 않습니다. HTTP 400/422처럼 입력이나 설정이 거부된 경우, 인증·권한·잔액 부족은 같은 요청을 반복하지 않고 원인을 표시합니다. AI 오류에는 단계·모델·허용된 오류 항목명과 실제 시도 횟수를 추가하며 키·요청 본문·제공자의 응답 원문은 출력하지 않습니다.

## 법령관리

법령명 검색 → 버전 조회 → 버전 선택 → **상하위법 확인 → 함께 수집 시작** 흐름을 사용합니다. 새 법령 수집 완료 시 왼쪽 카테고리에 자동으로 추가됩니다.

왼쪽 카테고리는 실제 조문 행이 저장된 법령만 표시합니다. 등록 이름이나 버전 정보만 남은 항목은 숨기며, 이런 빈 버전은 일괄 수집에서도 완료로 취급하지 않고 다시 수집합니다.

`lawService.do?target=lsStmd&MST=...&type=JSON`의 공식 체계도를 조회하며 **법률·시행령·시행규칙 세 종류만** 동반 수집합니다. 행정규칙·관련법령 목록은 자동으로 수집하지 않습니다. 시행규칙이 여러 개면 실제 부모·자식 관계를 유지하며 각각 표시합니다. 이름이 본법+시행규칙 형태가 아닌 규칙도 체계도에 있으면 포함합니다.

동반 법령의 MST·시행일·공포일이 체계도에 있으면 그 정보를 우선 사용합니다. 선택 법령의 연혁으로 적용 기간을 확인하고, 동반 항목의 정보가 없거나 선택 기간 밖/시행 예정인 경우에만 해당 법령 연혁에서 기준일 이하의 최신 버전을 찾습니다. 현재 선택 버전은 오늘, 과거 선택 버전은 다음 개정 직전을 묶음의 기준일로 삼습니다. 상위법 시행일이 더 오래됐다는 이유로 제외하지 않습니다. 과거의 모든 날짜를 자동으로 채우는 수집은 아니므로, 더 이른 질문 기준일의 참조 버전이 빠져 있으면 해당 버전을 추가 수집해야 합니다.

미리보기에는 함께 받을 버전, 기존 저장 여부, 확인되지 않은 항목을 보여줍니다. 이미 수집한 버전도 선택하여 누락된 상하위법만 보완할 수 있습니다. `law_hierarchy_snapshots`에는 체계도 관계와 버전 정보를, `collection_plans`에는 수집 계획을, `collection_history`에는 각 버전의 처리 결과를 저장합니다. 일부 실패를 상하위법 전체 완료로 표시하지 않으며 같은 작업을 다시 하면 완료된 본문은 건너뜁니다. 체계도 권한 오류/빈 응답은 관계가 없다고 간주하지 않고 오류로 안내합니다.

API 클라이언트는 `POST /api/management/collection-plan`에 기존 `items`를 보내고, 반환된 목록을 확인한 뒤 `POST /api/management/collections`에 `{"plan_id":"..."}`를 보냅니다. 계획은 1시간 유효합니다. 기존 `items` 직접 수집 API와 사전 수집 CLI의 단건 수집 동작은 호환성을 위해 유지됩니다.

### 현행 31개 법률 및 하위법·위임조문 수집

요청된 해양·환경 법률 31개와 공식 하위 시행령·시행규칙의 **현재 시행 버전 1세트씩** 수집하려면 앱 서버 종료 후 실행합니다.

```powershell
git pull
.\.venv\Scripts\python.exe -m app.preload_maritime
```

`--list-only`, `--law "선박안전법"`, `--names-file .\laws.txt`, `--data-dir`를 지원합니다. 완료된 본문은 재실행 시 건너뜁니다. 현행 명칭이 확인되지 않는 법은 과거 버전으로 대신 수집하지 않습니다. 결과는 `preload-maritime-report.json`과 수집 이력에 저장합니다.

세트 수집·위임관계 매핑 후 `data/html`의 **저장 파일에도 법·영 및 상하위 조문 링크를 자동 생성**합니다. 같은 폴더의 상대 HTML·조문 앵커를 사용해 파일을 직접 열어도 이동하며 별도 리빌드는 필요 없습니다. 터미널과 결과 JSON에 HTML 링크 생성 완료/실패 수를 표시합니다.

약칭 선언부의 `「법령 전체 이름」`은 대상 문서로, 바로 뒤 조번호와 이후 `법 제N조`·`영 제N조`는 해당 문서의 조문으로 연결합니다. 선언문과 항·호 원문은 유지하며 대상이 미수집이면 임의 링크를 생성하지 않습니다.

수집 중 개별 HTML은 먼저 저장되므로 해당 세트의 `HTML 링크 생성 완료` 로그가 나오기 전에는 상하위 링크가 아직 없을 수 있습니다. 이 중간 파일에는 준비 중 안내를 표시합니다. `법 제4조부터 제11조까지`나 `영 제2조 및 제3조`처럼 법령명이 생략된 범위·열거의 뒤 조문도 앞에서 명시한 법령을 이어받으며, 현재 시행령의 같은 번호로 연결하지 않습니다.

기존 상하위 본문의 **위임관계만** 보완하려면 `python -m app.backfill_delegation`을 실행합니다. API 원본과 조문별 관계를 저장하며 재임베딩은 없습니다. 상하위 조문은 LLM 입력과 화면 출처에 함께 포함하고, HTML에서도 상대 버전 문서로 연결합니다. [실행 옵션·관계 저장 구조·버전 검증 상세](docs/delegation.md)를 참고하세요.

### 현행 행정규칙 67개 수집

요청 목록 68행 중 띄어쓰기만 다른 `선령 20년 초과 내항 여객선의 선박검사기준`을 합친 **67개 행정규칙**을 수집합니다. 전체 목록은 [app/preload_admrul.py](app/preload_admrul.py)의 `RULES`에 있습니다. 앱 서버와 다른 수집 작업을 종료하고 프로젝트 폴더의 PowerShell에서 실행합니다. 기존 법령 DB·RAW·HTML은 그대로 유지하며 행정규칙을 추가합니다.

```powershell
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw "git pull 실패" }
.\collect_current_admrul.cmd
```

래퍼 대신 `.\.venv\Scripts\python.exe -m app.preload_admrul`로도 실행할 수 있습니다. 실행일의 한국 날짜를 기준으로 **현행 행정규칙 검색(`target=admrul&nw=1`) 결과 중 발령일·시행일이 기준일 이하인 최신 버전 하나**를 선택합니다. 공백을 제외한 정확한 이름만 일치시키며, 폐지·시행 예정·명칭 변경 등으로 현재 버전을 확인하지 못한 항목은 실패 사유를 남기고 나머지를 계속 처리합니다. 과거 연혁이나 이름이 비슷한 규칙으로 임의 대체하지 않습니다.

```powershell
# 본문·임베딩 없이 수집 대상 버전만 확인
.\collect_current_admrul.cmd --list-only
# 특정 규칙만 수집 또는 재시도
.\collect_current_admrul.cmd --rule "강선의 구조기준"
# 다른 목록: UTF-8 텍스트, 한 줄에 이름 하나
.\collect_current_admrul.cmd --names-file .\rules.txt
```

`--data-dir`로 별도 저장 경로도 지정할 수 있습니다. `.env`의 `LAW_API_OC`에 행정규칙 API 이용 권한이 있어야 하며, 실제 수집에는 임베딩 API 키가 필요합니다. 제목·본문만 임베딩하고 요약·예상 질문은 생성하지 않습니다. 상위 법령 수집이나 상하위 관계 자동 매핑은 이 명령에 포함하지 않습니다.

결과는 `DATA_DIR/preload-admrul-report.json`과 관리 화면의 수집 이력에 남습니다. 완료한 규칙은 재실행 시 건너뛰고 실패·중단·벡터 또는 RAW/HTML 누락 항목만 다시 처리합니다. 새 개정본이 현행으로 확인되면 그 버전 하나를 추가하며 이전 자료를 삭제하지 않습니다. 이미지/첨부파일만 있고 API에 본문 텍스트가 없는 규칙은 원문 XML과 추출 필요 사유를 남깁니다. 종료 코드 `0`은 전체 완료, `1`은 미완료/처리 오류, `2`는 실행 설정 오류, `130`은 사용자 중단입니다.

수집 후 서버를 다시 시작합니다.

```powershell
.\.venv\Scripts\python.exe -m app.serve --lan
```

### 기존 수집 자료 전체의 상하위법 보완

앱 서버를 `Ctrl+C`로 종료한 뒤 다음 명령을 실행합니다. 프로젝트 `.env`의 `LAW_API_OC`, `LLM_API_KEY`(또는 `OPENAI_API_KEY`), `DATA_DIR`를 사용합니다.

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m app.backfill_hierarchy
.\.venv\Scripts\python.exe -m app.serve --lan
```

실행 시작 시 DB에 있는 **모든 법령 수집 버전**을 대상으로 상하위 체계도를 조회합니다. 현재 버전만 대상으로 삼지 않으며, 행정규칙은 제외합니다. 체계도가 제공하는 법률·시행령·시행규칙의 버전 정보를 우선 사용하고 누락/기간 밖 정보는 앞서 설명한 방식으로 보완합니다. 새로 추가된 자료를 이번 실행의 출발점에 계속 추가하지 않아 무제한 재귀 수집을 방지합니다.

기존 본문·임베딩은 유지하고 미수집 버전만 수집·임베딩합니다. 여러 체계도에서 같은 버전이 나타나도 이번 실행에서는 한 번만 시도합니다. 중단되거나 일부 실패하면 **같은 명령을 다시 실행**하세요. 완료 판정은 DB를 사용하므로 보고서가 없어도 완료한 본문을 다시 다운로드·임베딩하지 않습니다. 재실행 때 체계도 조회는 다시 수행하고, 그 시점에 DB에 추가된 자료도 출발점에 포함합니다. 예전 수집본에 MST가 없으면 법령 식별자·시행일·공포일로 해당 버전이 유일하게 확인될 때만 MST를 보완합니다.

```powershell
# 조회만: 본문 다운로드·임베딩 없이 대상 확인
.\.venv\Scripts\python.exe -m app.backfill_hierarchy --list-only
# 특정 기존 법령만: 해당 법령의 저장된 모든 개정 버전 확인
.\.venv\Scripts\python.exe -m app.backfill_hierarchy --law "선박안전법 시행규칙"
```

`--data-dir "D:\LawRAG-data"`로 다른 DB 폴더도 지정할 수 있습니다. `--list-only`는 AI 키가 필요 없고 기존 수집 작업 상태를 바꾸지 않지만, 조회한 체계도·연혁·계획 및 식별자 보완은 DB에 저장합니다. 조회/수집 실패는 일반 실행에서 앱의 **법령관리 → 수집 이력**에 기록합니다. 상세 보고서는 `DATA_DIR/hierarchy-backfill-report.json`에 원자적으로 갱신하며, 파일 잠금으로 보고서 저장만 실패하면 경고 후 DB 수집을 계속합니다. 종료 코드 `0`은 완료, `1`은 일부 실패/미확인, `2`는 설정/대상 없음, `130`은 사용자 중단입니다.

HTML 뷰어는 `「법령명」(이하 “법”이라 한다)` 및 `「법령명 시행령」(이하 “영”이라 한다)` 선언을 해석합니다. `법 제N조`와 `영 제N조`는 각각 대상 문서로 연결하며 조문 뒤의 항·호 표기는 보존합니다. 선언이 없으면 공식 트리의 유일한 상위법을 사용하고, 모호하거나 본문이 미수집이면 링크를 만들지 않습니다. 이 매핑은 LLM 참조 문맥 확장에도 사용합니다. 앱은 채팅 출처 URL의 `as_of`를 기준으로 응답 링크를 생성합니다. 저장 파일은 수집 완료 시 확인한 기준일과 상대 파일 링크를 담으며 연결 대상 HTML도 같은 폴더에 있어야 합니다. 열람 중 API·임베딩 호출은 없습니다. 독립 실행용 `law_article_links.py`는 DB가 없는 단일 XML 변환기로, 기존 동일 문서 내부 링크 범위를 유지합니다.

사용자가 요청한 [부동산 관련 법령 사전 수집](docs/real_estate_catalog.md)은 화면 기능과 분리된 일회성 명령입니다. 기존 26개 명칭을 현행 기준으로 정리해 27개 대상으로 조회하며, 명칭이 바뀐 법령은 지정된 과거 명칭도 조회합니다. **전체 연혁을 조회한 뒤, 한국 날짜의 오늘까지 시행된 버전 중 법령별 최신 3개**를 저장하고 제목·본문 임베딩을 생성합니다. 시행 예정은 제외합니다. 미수록 지침은 실패로 기록하며 성공으로 처리하지 않습니다.

카테고리는 DB에 수집 버전이 있는 법령만 표시합니다. 이 사전 목록을 앱 시작 시 자동 등록하지 않으며, 과거 앱이 등록한 빈 항목도 표시하지 않습니다. 마지막 수집 버전을 삭제하면 카테고리 조회에서도 제외됩니다. HTML/XML 파일만 삭제하고 DB를 남긴 경우에는 수집 기록이 남아 있으므로 카테고리에 표시됩니다.

서버를 종료한 뒤 프로젝트 폴더에서 실행합니다. 기존 `.env`의 OC와 AI 키를 사용합니다.

```powershell
.\.venv\Scripts\python.exe -m app.preload_real_estate
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

수집 전에 전체 조회 건수와 최근 3개 대상을 확인하려면 아래 명령을 실행합니다. 본문 다운로드와 임베딩은 하지 않으며 AI 키도 사용하지 않습니다. `--law 소득세법`만 붙이면 소득세법만 수집합니다.

```powershell
.\.venv\Scripts\python.exe -m app.preload_real_estate --law 소득세법 --list-only
```

최근 3개 중 이미 임베딩한 버전은 건너뛰며, 대신 더 오래된 버전을 추가로 수집하지 않습니다. 3개 미만이면 조회된 대상만 처리합니다. 기존 데이터는 유지됩니다. DB의 연혁 식별키는 첫 실행 시 일련번호+시행일 기준으로 자동 업그레이드됩니다. 같은 일련번호에 시행일이 여러 개면 별도 버전이므로 사이트의 단순 연혁 건수와 API 시행 버전 건수는 다를 수 있습니다.

완료 후 기존 법령관리 화면에 모든 저장 버전이 표시됩니다. 항목별 결과는 `data/preload-real-estate-report.json`과 수집 이력에서 확인합니다. 중단 또는 일부 실패 시 같은 명령을 다시 실행하면 임베딩이 완료된 버전은 건너뛰고 누락된 버전을 처리합니다. 텍스트만 저장된 버전은 재수집·임베딩합니다. 전체 성공은 종료 코드 0, 일부 실패는 1, 필수 설정 누락은 2입니다. 이 명령은 실제 API에 접근 가능한 로컬 환경에서 실행해야 하며 Git pull만으로 데이터가 들어오는 것은 아닙니다.

1. **수집하기**를 누릅니다.
2. 법령명과 구분을 입력하고 **검색**합니다.
3. 검색 결과의 법령명 **버전 조회**를 누릅니다.
4. 현재 페이지의 **미수집 버전만 자동 체크**됩니다. 완료 또는 대기·실행 중인 항목은 제외합니다. 필요한 항목만 남길 수 있습니다. 페이지 변경 시 선택은 초기화됩니다.
5. **수집 시작**을 눌렀을 때만 API 본문 다운로드, 조문 제목·본문 임베딩을 실행합니다. 모두 성공해야 수집 완료로 표시합니다. OC 또는 AI 키가 없으면 수집 시작 전에 설정 오류를 안내합니다.
6. **수집 이력**에서 완료·실패·대기·실행·중단 상태와 실패 사유를 확인합니다. 완료한 버전은 서버에서도 중복 수집을 차단하며 실패한 항목은 재시도할 수 있습니다.
7. 수집된 개정 연혁에서 법령명을 누르면 하단에 조문 목록이 표시됩니다. 조문 버튼은 버전별 HTML의 해당 조로 이동하는 팝업을 엽니다.

API 이름 검색은 관련 법령도 반환할 수 있습니다. 법령 버전 조회는 `target=eflaw&nw=1,3`의 전체 페이지를 조회하여 연혁·현행 결과를 **일련번호+시행일**로 합칩니다. 오늘 이후 시행 예정 버전은 제외하고, 선택한 정확한 법령명(공백 차이 제외)으로 필터링한 뒤 건수·페이지를 계산합니다. 이름 검색 결과에 섞인 시행령·시행규칙은 해당 법률의 개정 건수에 포함하지 않습니다. 원격 연혁은 60초 동안 캐시하며 일부 페이지가 누락되거나 반복되면 오류로 표시합니다. API에서 제공하는 공포/발령·시행일을 표시하며 임의의 개정일을 만들지 않습니다. 현재 수집/목록/이력 페이지 크기는 10건입니다. 본문도 `target=eflaw&MST=일련번호&efYd=선택한시행일`로 요청하며 법령명·시행일이 다르면 저장하지 않고 실패 사유를 남깁니다.

기존 단일 벡터 색인 또는 키워드 전용 자료는 **버전 상세 → 제목·본문 재색인**으로 업그레이드할 수 있습니다. 저장된 XML을 사용하며 AI API 비용이 발생합니다. 원본이 없으면 재색인을 중단합니다.

## 기존 자료를 large 모델로 재임베딩

기존 `text-embedding-3-small` 벡터와 `text-embedding-3-large` 벡터는 함께 비교할 수 없습니다. 서버를 `Ctrl+C`로 종료한 뒤 실행하세요.

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m app.upgrade_models
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

이 명령은 `.env`의 임베딩 모델을 large, 초기 채팅 모델을 gpt-4.1로 설정합니다. API 키는 보존합니다. 저장된 XML 해시를 확인하고 DB에 보관한 **모든 개정 버전의 조문 제목·본문**을 재임베딩하므로 법령 API 재수집은 하지 않습니다. 임베딩 API 비용은 발생합니다. 버전별 모든 벡터가 성공해야 해당 버전을 갱신하며 실패한 버전은 기존 벡터를 보존합니다. 결과는 `data/model-upgrade-report.json`에 기록됩니다. 중단·실패 후 동일 명령을 재실행하면 완료한 버전은 건너뜁니다. 혼합 모델이 남은 상태에서는 하이브리드 검색을 중단하므로 실패 0건을 확인한 뒤 앱을 시작하세요. 채팅 모델만 바꾸는 경우에는 재임베딩이 필요하지 않습니다.

## 제목·본문 색인

수집 시 조문 제목과 본문만 `EMBEDDING_MODEL`(기본 `text-embedding-3-large`)로 임베딩합니다. 요약·예상 질문의 생성, 임베딩, 검색 참여, 보강 명령은 제거했습니다. 수집과 HTML 생성은 채팅용 GPT를 호출하지 않습니다. 채팅의 질문 재작성·관련성 검토·근거 충분성 판단·답변 생성은 유지합니다.

다른 조로 이동해 `제35조`처럼 번호만 남은 조문은 XML·HTML·DB에 보관하되 임베딩과 검색에서는 제외합니다. 빈 문자열을 API로 보내지 않으며 의도적으로 비워 둔 벡터를 재색인 실패로 판단하지 않습니다. 별지 **서식 파일**과 별표는 조문 임베딩 대상이 아닙니다. 다만 “별지 제1호서식을 제출해야 한다” 같은 **조문 본문의 제출 의무**는 법적 근거이므로 그대로 임베딩합니다. 별표의 텍스트와 참조 관계는 기존처럼 별도로 보관합니다.

긴 제목·본문은 UTF-8 기준 최대 8,000바이트씩 나눠 임베딩합니다. 이는 기본 `text-embedding-3` 계열의 토큰 한도보다 보수적인 상한이며 실제 토큰 수와 같지는 않습니다. 한글·이모지를 깨뜨리지 않고 문단/공백 경계를 우선합니다. 모든 구간의 벡터를 길이 가중 평균한 뒤 정규화해 조문당 하나의 벡터로 저장하며, 검색 근거·HTML·답변에 쓰는 원문은 자르지 않습니다. 일반적인 짧은 입력의 벡터는 그대로 유지합니다. 별도 토크나이저 설치나 다운로드는 필요 없습니다.

같은 모델의 제목·본문 벡터가 이미 있으면 재수집·재임베딩 없이 사용할 수 있습니다. 이전 DB의 요약·질문 테이블은 자동 삭제하지 않지만 조회·검색·점수 계산에 사용하지 않습니다. 새 DB에는 해당 테이블을 만들지 않으며 기존 `.env`의 `METADATA_MODEL` 값도 사용하지 않습니다. 이전 `app.enrich_metadata` 명령은 더 이상 실행하지 마세요.

업데이트하려면 진행 중인 수집과 서버를 종료한 뒤 `git pull --ff-only origin main`을 실행하고 서버를 다시 시작하세요. 관리 화면에서 실패한 수집을 다시 시도하거나 `python -m app.preload_maritime`을 다시 실행할 수 있습니다. 완료된 버전은 재사용하고 미완료 버전만 수집합니다.

## 시점별 검색

- 기본은 한국 시간의 오늘까지 시행된 **수집 버전 중 가장 최신**입니다. 시행 예정 버전을 현재 법으로 사용하지 않습니다.
- `2020년 6월 1일 기준 …`, `2020-06-01 기준 …` 질문이나 `/api/search`, `/api/chat`의 `as_of` 날짜로 해당 시점의 버전을 선택합니다.
- 연도만 지정하거나 기간·당시 같은 표현은 날짜를 다시 묻습니다. 기간 전체의 모든 개정 비교 및 대화 맥락에서 날짜 추론은 아직 하지 않습니다.
- API에서 확인한 적용 버전이 미수집이면 오래된 버전으로 대신 답하지 않습니다.
- API에서 **조회한 페이지와 저장된 버전만** 알고 있으므로 모든 개정의 수집 완료나 전국 법령의 최신성을 보증하지 않습니다. 폐지·경과조치·소급적용·조문별 별도 시행일 판단, 법령명 변경에 따른 계보 통합은 별도 확장이 필요합니다.

## 제목·본문 검색 점수

채팅은 **법령명을 입력하지 않아도** 질문만으로 기준일에 시행 중인 수집 법령 전체를 검색합니다.

1. **질문 재조정**: 일상어를 법령 검색 용어로 정리합니다. 원문과 rewrite를 각각 검색하며 원래 질문·수치·부정 조건·기준일을 최종 답변까지 유지합니다. rewrite에 등장한 법령명으로 범위를 제한하지 않습니다.
2. **관련 법조항 검색**: 원문/rewrite 각각 조문 제목·본문의 키워드·임베딩 검색을 실행합니다. 같은 조문이 여러 경로에서 검색되면 하나로 합칩니다. 법령명은 작은 보조 점수이며, 일반적인 조 제목 때문에 본문 근거가 탈락하지 않도록 제목 최소 점수 조건을 없앴습니다. 원문에 명시한 법령명+조번호는 직접 조회 경로로 보충합니다.
3. **상위 15개 검토 후 관계 확장·검토**: 임계치를 통과한 검색 결과를 선택한 방식의 점수순으로 정렬하고 최대 15개만 LLM이 검토합니다. 원문/rewrite 결과는 합쳐서 15개이며 추가 검색에서도 동일하게 제한합니다. 항·호·목만 잘라 보내지 않고 조 전체를 전달해 도입 문구·모두/어느 하나·단서를 보존합니다. 통과한 부모 조문에서 확장한 상하위 연결 조문도 최대 15개를 묶어 별도 검토하고, 통과한 조문만 답변과 화면 출처에 포함합니다. 일반 정의·별표·참조 문맥은 종전처럼 LLM 전용일 수 있습니다. 같은 요청에서 이미 판정한 조문은 추가 검색에서도 재검토하지 않으며 탈락한 검색·연결 후보는 다른 경로로 다시 추가하지 않습니다.
4. **근거 충분성 확인**: 부족한 법적 근거와 사용자 정보를 구분합니다. 법적 근거가 부족하면 첫 검색에서 확인한 용어·관계를 바탕으로 다른 검색어 최대 2개로 **한 차례만** 추가 검색하고 다시 검토합니다. 원래 질문/기준일은 고정하며 단순 재검색은 방지합니다. 사용자 정보만 부족하면 반복 검색하지 않습니다.
5. **근거 기반 답변**: 확보된 본문만 사용하고 아직 부족한 쟁점이나 사실은 구분해 안내합니다. 최종 근거를 선택한 점수순으로 정렬한 뒤 인용 번호를 부여합니다.

추가 검색은 **이미 수집한 DB 내부**에서만 수행합니다. 없는 법령을 자동 다운로드하거나 부족한 계약일·금액 등을 추측하지 않습니다. 전용 Reranker는 사용하지 않습니다.

후보 검토는 최대 15개를 한 번의 요청으로 묶습니다. 전체 본문을 보존한 입력이 약 60,000자를 넘으면 묶음을 나눠 **최대 두 묶음을 병렬 처리**합니다. 같은 본문을 검색 위치 정보에 중복해서 넣지 않으며, GPT-5 계열은 후보 검토에 한해 `reasoning_effort=low`를 사용합니다. 지원 모델에는 JSON Schema를 지정하고 후보 번호·판정 수·역할을 검증합니다. JSON 형식, 번호 누락·중복, 응답 중단 등이 발생하면 **실패한 묶음만 한 번 재시도**합니다. 계속 실패하면 구체적인 실패 유형을 안내하며 검증되지 않은 후보로 답하지 않습니다. `app.evidence_review`의 INFO 로그를 활성화하면 `Evidence review` 항목에서 후보·묶음 수와 처리 시간을 확인할 수 있으며, API 키나 원문 응답은 기록하지 않습니다. 형식 오류 유형은 WARNING 로그로 남깁니다. 실제 지연은 조문 길이와 선택 모델·API 상태에도 영향을 받습니다.

`POST /api/chat/stream`은 각 실제 단계 시작 시 NDJSON `stage` 이벤트를 전송하고, 마지막에 `result` 또는 `error` 이벤트를 보냅니다. 화면은 타이머가 아닌 이 이벤트로 상태를 바꾸며 **현재 처리 단계 하나만** 표시합니다. 다음 단계가 시작되면 같은 자리의 문구를 교체하고, 완료·대기 단계 목록은 쌓지 않습니다. 추가 검색과 재검토도 실제 실행될 때 표시하며 답변 또는 오류가 도착하면 진행 표시를 닫습니다. 근거가 없으면 답변 생성 단계는 실행하지 않습니다. `POST /api/chat`도 동일한 검증 흐름의 JSON 결과를 제공합니다. `POST /api/search`는 별도의 검색 전용 API로 LLM 관련성 필터를 적용하지 않습니다. 검색 전용 API의 키워드 모드는 AI 호출 없이 작동하지만, 채팅은 키워드 모드에서도 재작성·관련성 검증·답변에 AI를 사용합니다.

채팅창에서 `gpt-4o-mini`, `gpt-4o`, `gpt-4.1`, `gpt-5.4` 등 모델을 선택할 수 있습니다. `/models`에서 조회한 GPT 모델도 추가하며 이후 모델은 ID 직접 입력으로 사용할 수 있습니다. 목록 표시는 해당 모델의 실행 권한을 보장하지 않으며, 선택한 모델을 사용할 수 없으면 오류를 표시하고 다른 모델로 조용히 바꾸지 않습니다. Chat Completions 호환 모델만 지원합니다. 선택한 모델은 그 요청의 재작성·검토·답변에만 적용되며 임베딩 모델이나 다른 대화의 요청을 변경하지 않습니다.

답변은 Markdown으로 표시하며 제목·굵은 글씨·중첩 목록·표·인용문·코드를 지원합니다. 한글 조사 앞의 따옴표·괄호가 포함된 강조도 처리합니다. 저장된 이전 답변에도 같은 표시 방식을 적용하며, 사용자 질문과 복사할 원문은 그대로 보존합니다. HTML을 실행하지 않고 안전한 링크만 렌더링합니다.

답변의 `[1]`은 추천 근거 목록의 순번이며 제1조라는 뜻이 아닙니다. 번호에 마우스를 올리면 법령·조문명이 나오고, 클릭하거나 키보드로 실행하면 오른쪽 지식출처에서 해당 조문을 강조합니다. 없는 번호나 코드·링크 안의 번호는 근거 버튼으로 바꾸지 않습니다. 답변 아래의 출처는 법령별 버튼 하나로 묶고 그룹 내 최고 점수 순으로 표시합니다. 버튼을 누르면 해당 답변·법령의 조문만 점수순으로 표시하고, 조문을 누르면 정확한 버전의 HTML이 열립니다.

일반 참조·역참조·별표·정의 문맥은 LLM 참고자료로 전달합니다. 공식 위임조문 비교 또는 상하위 참조로 확인한 조문은 별도 LLM 관련성 검토를 통과해야 `include_in_sources=true`로 응답의 `evidence`와 화면 출처에 포함합니다. LLM에는 연결된 조문의 전체 본문, 출발 법령·조문, 연결 유형·방향을 제공합니다. 숫자 인용은 검색·상하위 검토를 통과한 표시 대상 근거에 부여합니다. 화면에서 숨기는 일반 연결 자료만 뒷받침하는 설명은 답변 본문에서 실제 법령명·조문명을 밝히도록 지시하며, 출발 조문에 없는 내용을 그 조문에서 인용하지 않도록 합니다. 새 표시 플래그가 없는 이전 대화는 일반 연결 근거와 해당 인용 표시를 숨기되 나머지 원래 번호는 유지해 잘못된 조문으로 이동하지 않게 합니다. 같은 조문이 검색으로 직접 선정된 경우에는 추천 근거로 표시됩니다.

기존 제목·본문 벡터를 검색에 재사용합니다. 제목 키워드는 **조문 제목만**, 제목 의미 검색은 **법령명 - 조번호(조문 제목)** 임베딩을 비교합니다. 본문은 별도로 저장한 본문 임베딩과 키워드를 비교합니다. 원문 검색 경로에서는 제목 일치만으로 후보가 되지 않게 본문 적합도 조건을 유지합니다. 원질의와 rewrite는 한 번의 임베딩 요청으로 처리하고 같은 질의 벡터를 모든 필드에 사용합니다. 항·호·목 위치 검색도 기존 원문에서 처리합니다. 본문 키워드 점수는 질의 포함률 0.8 + 해당 구간의 일치 비율 0.2로 계산하고 조 전체/항·호·목 중 최고값을 사용하므로, 긴 조의 서로 떨어진 단어 일치보다 한 구간에 모인 일치를 우선합니다. 같은 모델의 제목·본문 벡터가 있으면 원문 재수집·재임베딩 없이 그대로 사용합니다. 제목·본문 벡터 누락·모델 불일치·차원 불일치는 오류로 안내하며 키워드 모드는 벡터 없이도 동작합니다. 항·호별 별도 임베딩 색인은 아직 사용하지 않습니다.

가중합의 원문 경로는 `본문 점수 = 0.65 × 본문 코사인 유사도 + 0.35 × 본문 키워드 점수`, `원문 경로 점수 = 0.80 × 본문 점수 + 0.20 × 조문 제목 키워드 점수 + 명시 법령명 가산점(최대 0.03)`이며 상한은 1입니다. 이 경로는 본문 0.20 및 최종 임계치(기본 0.48)를 통과해야 합니다. 명시한 법령+조번호 직접 조회는 식별자 경로로 취급합니다.

구형 `SEARCH_TITLE_WEIGHT`, `SEARCH_MIN_TITLE_SCORE`, `SEARCH_MIN_BODY_SCORE`는 새 채팅/API 검색에 사용하지 않습니다.

채팅 화면 오른쪽 위 **톱니바퀴 → 검색 설정**에서 검색 방식, 근거 임계치, **가중합 / RRF 순위 결합**을 설정하고 적용합니다. 평상시 입력창에는 검색 옵션을 노출하지 않습니다. RRF는 **필드 안의 검색 방식 결합 → 제목·본문 필드 결합** 두 단계로 계산합니다.

1. **제목 순위**: 원질의/rewrite별 제목 키워드·제목 임베딩 상위 50개 목록을 `Σ 1/(60+순위)`로 합쳐 제목 후보 상위 50개를 정합니다.
2. **본문 순위**: 같은 방식으로 본문 키워드·본문 임베딩 목록을 합쳐 본문 후보 상위 50개를 정합니다.
3. **최종 순위**: 제목·본문 두 필드의 순위를 `Σ 1/(60+필드 순위)`로 결합합니다. 어느 필드에 없는 조문은 그 필드에서 0점을 받습니다. 키워드 모드도 필드를 분리하며 임베딩 목록만 사용하지 않습니다. 원질의에 명시된 법령+조번호 직접 조회는 필드 순위의 상단에 배치하고, 별도의 가산 목록을 만들지 않습니다.

표시 점수는 `최종 RRF 원점수 / (2/61) × 100`입니다. 원질의/rewrite 개수가 최종 분모를 늘리지 않습니다. 두 필드 모두 1위면 100점이며, 한 필드만 1위이고 다른 필드에 없으면 50점입니다. RRF는 원점수 차이를 반영하지 않으며 점수는 정확도·관련성의 확률이 아닙니다. 후보는 제목·본문 가중합 임계치 및 본문 적합도 조건을 통과해야 합니다. **화면에는 선택한 방식의 점수 하나를 ‘관련도 점수’로 통일**하여 별도 줄의 파란색 굵은 숫자로 표시하고 그다음 줄에 시행일을 표시합니다. 필드별 내부 점수는 화면에 노출하지 않습니다. 연결 자료의 점수는 내부 문맥 예산에만 쓰며 화면에 표시하지 않습니다. 표시 대상 상하위 자료는 대신 ‘상하위 연결 근거’로 표시합니다.

동일 입력과 임베딩 호출로 가중합/RRF를 비교하려면 `POST /api/search/compare`에 `question`, `mode`, `threshold`, `limit`, `as_of`를 보냅니다. API가 rewrite를 1회 수행한 뒤 `weighted`, `rrf`, `queries`, `threshold_basis`를 반환합니다. 최종 LLM 답변은 생성하지 않습니다. 또는 CLI에서 직접 검색용 문장을 지정할 수 있습니다.

```powershell
.\.venv\Scripts\python.exe -m app.cli search "서울 전세보증금 보호" --rewrite "서울 소액임차인 우선변제 금액" --compare
```

가중합을 기본으로 유지합니다. RRF가 더 낫다고 가정하지 않았으며, 실제 질의와 정답 근거 묶음을 라벨링한 Recall@K/필수 근거 확보율 비교가 별도로 필요합니다. API는 `weighted_score`, `rrf_score`, `law_name_score`, `title_score`, `body_score`, `matched_units`를 제공합니다. `title_score`는 기존 가중합·임계치용 제목 키워드 점수이며, 제목 의미 점수는 `title_semantic_score`로 구분합니다. 최종 RRF 계산은 `rrf_field_ranks`의 제목/본문 순위(null은 해당 목록에 없음), `rrf_raw_score`, `rrf_max_score`로 확인할 수 있습니다. 비교 API의 `rrf_strategy=field_hierarchical`, `rrf_fields`, `rrf_constant`도 계산 방식을 명시합니다. API의 `score`/`rrf_score`는 0~1이며 화면에서 100을 곱해 표시합니다.

## 참조 조문·별표 연결

SQLite의 저장 조문·별표와 참조 원문을 사용합니다. 기존 자료도 재수집 없이 새 관계 탐색을 사용하며 Graph DB나 별도 Reranker 서버는 필요하지 않습니다.

- **정방향**: 같은 법령의 조문, 명시한 다른 법령의 조문, 일반 텍스트 별표를 연결합니다. 제목뿐 아니라 전체 본문·단위·주석도 LLM에 제공합니다.
- **역방향**: 찾은 조문을 인용하는 제재·예외 조문이나 시행령·시행규칙을 찾습니다. “대통령령으로 정한다”만으로 조번호를 만들지 않고, 해당 법 조문을 실제 인용한 시행령 본문에서 연결을 확인합니다.
- **대상 식별**: 명시된 법명, `이하 "법"이라 한다` 같은 선언, 명칭이 일치하는 본법–시행령–시행규칙 계열을 사용합니다. 모호한 ‘같은 법’이나 미수집 대상은 임의 연결하지 않습니다.
- **시점**: 같은 법령의 참조는 같은 버전으로, 다른 법령과 역참조는 질문 기준일에 유효한 수집 버전으로 연결합니다. 최신 적용 버전이 미수집인 것으로 확인되면 오래된 버전으로 대신 연결하지 않습니다.
- **문맥**: 같은 법령의 정의 조문도 보조 문맥 후보로 추가합니다. 실제 인용 관계와 문맥 보충 관계를 구분하고 `reference_edges`에 출발/도착 버전·조문·관계·원문 발췌를 응답 메타데이터로 기록합니다.
- 본문 일반 참조는 직접 연결 1단계, 위임조문 관계는 상위/하위 각각 최대 2단계를 탐색하며 추가 검색이 실행되면 새 근거에서 다시 1단계 탐색할 수 있습니다. 확장 개수, 입력 본문 길이, 최종 문서 수(40)를 제한하고 제한 때문에 빠진 문서는 누락 목록으로 남깁니다. 조문 중간을 잘라 단서를 제거하지 않습니다.
- 텍스트 없는 PDF/HWP/이미지 별표의 OCR, 부칙·경과조치의 적용 판단, 자동 법령 계보 추적은 아직 지원하지 않습니다. 미확보 참조는 충분성 점검에 전달하며 없는 내용을 생성하지 않습니다.

법령 본문은 조·항·호·목의 개행을 보존합니다. 행정규칙은 구조화된 조문 XML, 전체 본문 CDATA, HTML 단락·줄바꿈·표, 번호 목록 형식을 처리합니다. 원문에 실제 조 번호가 있으면 해당 조로 분리하고, 번호 목록형 지침은 원문에 없는 조 번호를 만들지 않고 `본문 구간 N`으로 저장합니다. 텍스트 없는 이미지·첨부파일 전용 응답은 OCR/파일 추출이 필요하므로 실패 처리합니다. 파싱 실패 시에도 원문 XML을 보관하고 수집 이력에 파일 위치를 남깁니다. 원문에 없는 수식·별표 내용을 생성하지 않습니다.

UI는 로컬에 포함한 Pretendard Variable 글꼴과 SVG 말풍선·법령 아이콘을 사용합니다. 외부 폰트 CDN을 호출하지 않아 내부망에서도 같은 글꼴로 표시합니다. 글꼴 라이선스는 `frontend/licenses/Pretendard-OFL.txt`에 포함합니다.

## HTML만 전체 재생성

본문의 `별표 1`, `별표2`, `별표 10`, `별표 1의2` 등은 같은 수집 버전의 별표 위치로 연결됩니다. 별표 본문 안의 조문·별표 참조도 연결합니다. 다른 법령·불명확한 대상·XML에 없는 별표는 자동 연결하지 않습니다. 텍스트가 없고 공식 파일 주소만 있는 별표는 해당 위치에 본문 미확보 안내와 원문 파일 링크를 표시합니다.

API의 별표번호 `0`/`000000`은 번호 없는 별표로 표시합니다. 본문의 `별표와 같다`, `[별표]` 등은 이 대상이 있을 때 연결하며, 번호 있는 별표를 임의로 선택하지 않습니다. 기존 출처와의 호환을 위해 내부 매핑 키와 `법령명-별표0` 앵커는 유지하지만 화면 제목에는 `별표 0` 대신 `별표`가 표시됩니다. 이 표시·링크 수정도 HTML 재생성만으로 적용됩니다.

로컬 프로젝트에서 아래 명령을 실행하면 **과거 버전과 행정규칙을 포함한 모든 수집 버전**의 HTML을 보관 XML로 다시 만듭니다.

```powershell
git pull
.\.venv\Scripts\python.exe -m app.rebuild_html
```

`.env`의 `DATA_DIR`을 사용하며 다른 폴더는 `--data-dir 경로`로 지정합니다. API 호출과 재임베딩 없이 HTML만 교체합니다. DB는 읽기 전용으로 열며 원문 XML과 기존 출처 URL·앵커는 유지합니다. XML이 없거나 해시가 다르면 해당 HTML을 유지하고 실패를 출력한 뒤 나머지를 계속 처리합니다. 갱신 코드를 앱에도 적용하려면 서버를 재시작하세요. 구형 HTML은 앱에서 열 때에도 같은 버전 XML로 갱신됩니다.

다른 개발자에게 전달할 독립 파일은 `law_article_links.py`입니다. 표준 라이브러리만 사용하며 `python law_article_links.py law.xml -o law.html`로 XML 한 건을 변환합니다. 앱의 저장 자료 전체 갱신에는 위의 `app.rebuild_html` 명령을 사용하세요.

## 프론트엔드 개발

React 소스는 `frontend/src/`, 빌드 결과는 `app/static/`입니다. **빌드 결과를 직접 수정하지 마세요.** Node.js 22 LTS 이상을 권장합니다.

```powershell
cd frontend
npm ci
npm run build
```

빌드 후 Python 서버가 결과를 제공합니다. 프론트 개발 서버가 필요하면 `npm run dev`를 사용합니다. `/api`, `/documents`는 로컬 Python 8001로 프록시됩니다. 프론트 개발 포트의 POST도 동일 출처 검사에 통과하도록 Vite의 기본 원본 Host 전달을 유지합니다. 별도 배포 시 출처 정책을 점검하세요.

## 저장 구조

- `data/raw/<해시>.xml`: API 원본
- `data/html/<해시>.html`: 버전별 HTML. `법령명-제N조`, `법령명-별표N` 앵커
- `data/laws.sqlite3`: 카테고리, 개정 버전, 제목/본문 벡터, 참조 관계, 수집 작업 이력
- sqlite-vec 코사인 거리로 정확 검색합니다. 대규모 ANN 전용 DB는 아닙니다.
- 기존 DB는 추가 테이블/컬럼으로 마이그레이션합니다. 과거 HTML·조문을 삭제하지 않습니다. 구형 색인은 재색인 전 키워드 검색만 가능합니다.
- 대화는 현재 브라우저 localStorage에 저장됩니다. 서버에 채팅 이력을 저장하지 않습니다.
