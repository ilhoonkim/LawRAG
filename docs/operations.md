# 운영·개발 명령 모음

전체 구성과 기본 설정은 [README](../README.md)를 참고하세요. 아래 PowerShell 명령은 프로젝트 루트에서 실행합니다. CLI로 자료를 변경하기 전에는 앱 서버와 다른 수집 작업을 종료합니다.

## 내부망 연결 확인

Windows 방화벽에 해당 포트가 허용되지 않은 경우 **서버 PC의 관리자 PowerShell**에서 다음 명령을 한 번 실행합니다. 도메인/개인 네트워크의 같은 서브넷에만 허용하며 방화벽 전체를 끄지 않습니다.

```powershell
New-NetFirewallRule -DisplayName "LawRAG LAN 8001" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8001 -RemoteAddress LocalSubnet -Profile Domain,Private
```

서로 다른 사내 서브넷/VLAN에서도 사용할 때는 회사의 실제 내부망 대역을 `RemoteAddress`에 지정하고 망 사이 접근 정책을 확인해야 합니다. Windows 네트워크 프로필이 공용이면 위 규칙이 적용되지 않습니다. 포트를 바꿨다면 방화벽 포트도 맞추세요. 다른 PC에서 `Test-NetConnection 서버IPv4주소 -Port 8001`로 연결을 확인할 수 있습니다.

- **공유되는 것**: 법령 DB, 수집 상태·이력, 법령관리 기능, 서버의 API 설정. 현재 접속자는 모두 법령관리 기능도 사용할 수 있습니다.
- **분리되는 것**: 채팅 제목·질문·답변은 각 브라우저의 localStorage에만 보관합니다. 요청 시 해당 브라우저가 보낸 대화만 답변 문맥으로 사용하며, 다른 브라우저에 이력을 내려주는 서버 API는 없습니다.
- 로그인 대신 **브라우저 프로필 단위**로 구분합니다. 같은 PC·같은 프로필을 공유하면 이력도 공유하고, 다른 PC/브라우저에서는 자동 동기화되지 않습니다. 시크릿 창을 닫거나 사이트 데이터를 지우면 이력이 사라집니다.
- `http://127.0.0.1:8001`과 `http://내부IP:8001`은 저장소가 달라 이력이 별개로 보입니다. 기존 이력이 삭제된 것은 아니며 원래 주소로 접속하면 볼 수 있습니다. 주소/포트가 달라져도 같습니다.

## AI 연결과 재시도

수집 중 AI 요청이 실패하면 `python -m app.check_ai`로 임베딩 연결을 확인합니다. 키의 존재와 설정 위치만 표시하며 키 값은 출력하지 않습니다. PowerShell 등 프로세스 환경변수는 `.env`보다 우선합니다. 이 진단은 짧은 문장 1개로 실제 임베딩 API를 호출하며 DB를 수정하지 않습니다. 연결에 성공해도 법령 본문의 길이·입력 형식 문제는 별도로 확인해야 합니다. 수집 화면과 이력에는 HTTP 상태 및 오류 종류를 표시합니다. 예를 들어 401은 인증, `429 / insufficient_quota`는 API 결제·잔액, `429 / rate_limit_exceeded`는 요청량 제한입니다. 과거 이력에 저장된 공통 오류 문구는 재시도 전까지 유지됩니다.

법령 다운로드와 AI 요청의 시간 초과·일시적 연결 오류, HTTP 408/409/425/429 및 재시도 가능한 5xx는 **최초 요청 후 최대 3회** 더 시도합니다. 기본 대기는 약 2·4·8초이며 서버의 `Retry-After`는 최대 60초까지 반영합니다. 이 자동 재시도 중에는 이미 성공한 임베딩 배치를 다시 보내지 않습니다. HTTP 400/422처럼 입력이나 설정이 거부된 경우, 인증·권한·잔액 부족은 같은 요청을 반복하지 않고 원인을 표시합니다. AI 오류에는 단계·모델·허용된 오류 항목명과 실제 시도 횟수를 추가하며 키·요청 본문·제공자의 응답 원문은 출력하지 않습니다.

## 기존 수집 자료 관리

### 상하위법 보완

앱 서버를 `Ctrl+C`로 종료한 뒤 다음 명령을 실행합니다. 프로젝트 `.env`의 `LAW_API_OC`, `LLM_API_KEY`(또는 `OPENAI_API_KEY`), `DATA_DIR`를 사용합니다.

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m app.backfill_hierarchy
.\.venv\Scripts\python.exe -m app.serve --lan
```

실행 시작 시 DB에 있는 **모든 법령 수집 버전**을 대상으로 상하위 체계도를 조회합니다. 현재 버전만 대상으로 삼지 않으며, 행정규칙은 제외합니다. 체계도가 제공하는 법률·시행령·시행규칙의 버전 정보를 우선 사용하고 누락/기간 밖 정보는 [README의 버전 선택 방식](../README.md#api-조회와-버전-선택)으로 보완합니다. 새로 추가된 자료를 이번 실행의 출발점에 계속 추가하지 않아 무제한 재귀 수집을 방지합니다.

기존 본문·임베딩은 유지하고 미수집 버전만 수집·임베딩합니다. 여러 체계도에서 같은 버전이 나타나도 이번 실행에서는 한 번만 시도합니다. 중단되거나 일부 실패하면 **같은 명령을 다시 실행**하세요. 완료 판정은 DB를 사용하므로 보고서가 없어도 완료한 본문을 다시 다운로드·임베딩하지 않습니다. 재실행 때 체계도 조회는 다시 수행하고, 그 시점에 DB에 추가된 자료도 출발점에 포함합니다. 예전 수집본에 MST가 없으면 법령 식별자·시행일·공포일로 해당 버전이 유일하게 확인될 때만 MST를 보완합니다.

```powershell
# 조회만: 본문 다운로드·임베딩 없이 대상 확인
.\.venv\Scripts\python.exe -m app.backfill_hierarchy --list-only
# 특정 기존 법령만: 해당 법령의 저장된 모든 개정 버전 확인
.\.venv\Scripts\python.exe -m app.backfill_hierarchy --law "선박안전법 시행규칙"
```

`--data-dir "D:\LawRAG-data"`로 다른 DB 폴더도 지정할 수 있습니다. `--list-only`는 AI 키가 필요 없고 기존 수집 작업 상태를 바꾸지 않지만, 조회한 체계도·연혁·계획 및 식별자 보완은 DB에 저장합니다. 조회/수집 실패는 일반 실행에서 앱의 **법령관리 → 수집 이력**에 기록합니다. 상세 보고서는 `DATA_DIR/hierarchy-backfill-report.json`에 원자적으로 갱신하며, 파일 잠금으로 보고서 저장만 실패하면 경고 후 DB 수집을 계속합니다. 종료 코드 `0`은 완료, `1`은 일부 실패/미확인, `2`는 설정/대상 없음, `130`은 사용자 중단입니다.

HTML 뷰어는 `「법령명」(이하 “법”이라 한다)` 및 `「법령명 시행령」(이하 “영”이라 한다)` 선언을 해석합니다. `법 제N조`와 `영 제N조`는 각각 대상 문서로 연결하며 조문 뒤의 항·호 표기는 보존합니다. 선언이 없으면 공식 트리의 유일한 상위법을 사용하고, 모호하거나 본문이 미수집이면 링크를 만들지 않습니다. 이 매핑은 LLM 참조 문맥 확장에도 사용합니다. 앱은 채팅 출처 URL의 `as_of`를 기준으로 응답 링크를 생성합니다. 저장 파일은 수집 완료 시 확인한 기준일과 상대 파일 링크를 담으며 연결 대상 HTML도 같은 폴더에 있어야 합니다. 열람 중 API·임베딩 호출은 없습니다. 독립 실행용 `law_article_links.py`는 DB가 없는 단일 XML 변환기로, 기존 동일 문서 내부 링크 범위를 유지합니다.

### 위임관계만 보완

이미 상하위 본문이 있다면 다음 명령으로 API 관계만 보완합니다. 재임베딩하지 않으며 상세 동작은 [위임관계 문서](delegation.md)를 참고하세요.

```powershell
.\.venv\Scripts\python.exe -m app.backfill_delegation
```

### 임베딩 모델 변경

기존 `text-embedding-3-small` 벡터와 `text-embedding-3-large` 벡터는 함께 비교할 수 없습니다. 서버를 `Ctrl+C`로 종료한 뒤 실행하세요.

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m app.upgrade_models
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

이 명령은 `.env`의 임베딩 모델을 large, 초기 채팅 모델을 gpt-4.1로 설정합니다. API 키는 보존합니다. 저장된 XML 해시를 확인하고 DB에 보관한 **모든 개정 버전의 조문 제목·본문**을 재임베딩하므로 법령 API 재수집은 하지 않습니다. 임베딩 API 비용은 발생합니다. 버전별 모든 벡터가 성공해야 해당 버전을 갱신하며 실패한 버전은 기존 벡터를 보존합니다. 결과는 `data/model-upgrade-report.json`에 기록됩니다. 중단·실패 후 동일 명령을 재실행하면 완료한 버전은 건너뜁니다. 혼합 모델이 남은 상태에서는 하이브리드 검색을 중단하므로 실패 0건을 확인한 뒤 앱을 시작하세요. 채팅 모델만 바꾸는 경우에는 재임베딩이 필요하지 않습니다.

### HTML만 전체 재생성

본문의 `별표 1`, `별표2`, `별표 10`, `별표 1의2` 등은 같은 수집 버전의 별표 위치로 연결됩니다. 별표 본문 안의 조문·별표 참조도 연결합니다. 다른 법령·불명확한 대상·XML에 없는 별표는 자동 연결하지 않습니다. 텍스트가 없고 공식 파일 주소만 있는 별표는 해당 위치에 본문 미확보 안내와 원문 파일 링크를 표시합니다.

API의 별표번호 `0`/`000000`은 번호 없는 별표로 표시합니다. 본문의 `별표와 같다`, `[별표]` 등은 이 대상이 있을 때 연결하며, 번호 있는 별표를 임의로 선택하지 않습니다. 기존 출처와의 호환을 위해 내부 매핑 키와 `법령명-별표0` 앵커는 유지하지만 화면 제목에는 `별표 0` 대신 `별표`가 표시됩니다. 이 표시·링크 수정도 HTML 재생성만으로 적용됩니다.

로컬 프로젝트에서 아래 명령을 실행하면 **과거 버전과 행정규칙을 포함한 모든 수집 버전**의 HTML을 보관 XML로 다시 만듭니다.

```powershell
git pull --ff-only origin main
.\.venv\Scripts\python.exe -m app.rebuild_html
```

`.env`의 `DATA_DIR`을 사용하며 다른 폴더는 `--data-dir 경로`로 지정합니다. API 호출과 재임베딩 없이 HTML만 교체합니다. DB는 읽기 전용으로 열며 원문 XML과 기존 출처 URL·앵커는 유지합니다. XML이 없거나 해시가 다르면 해당 HTML을 유지하고 실패를 출력한 뒤 나머지를 계속 처리합니다. 갱신 코드를 앱에도 적용하려면 서버를 재시작하세요. 구형 HTML은 앱에서 열 때에도 같은 버전 XML로 갱신됩니다.

다른 개발자에게 전달할 독립 파일은 `law_article_links.py`입니다. 표준 라이브러리만 사용하며 `python law_article_links.py law.xml -o law.html`로 XML 한 건을 변환합니다. 앱의 저장 자료 전체 갱신에는 위의 `app.rebuild_html` 명령을 사용하세요.

## 프론트엔드 개발

React 소스는 `frontend/src/`, 빌드 결과는 `app/static/`입니다. **빌드 결과를 직접 수정하지 마세요.** Node.js 22 LTS 이상을 권장합니다.

```powershell
cd frontend
npm ci
npm run build
cd ..
```

빌드 후 Python 서버가 결과를 제공합니다. 프론트 개발 서버가 필요하면 `npm run dev`를 사용합니다. `/api`, `/documents`는 로컬 Python 8001로 프록시됩니다. 프론트 개발 포트의 POST도 동일 출처 검사에 통과하도록 Vite의 기본 원본 Host 전달을 유지합니다. 별도 배포 시 출처 정책을 점검하세요.

## 검색 진단과 검증

### 점수 계산 상세

명사 분석은 `kiwipiepy`로 질문과 일치 지점의 짧은 어절에 수행합니다. `단독경보형감지기는`의 조사를 분리하고 `단독 경보형 감지기`처럼 띄어 쓴 복합 명칭도 보존합니다. `기준·사항·규정` 같은 공통 명사는 독립 검색어에서 제외하되 `의장수`의 `수`처럼 앞 명사에 붙은 구성 음절은 복합어에 보존합니다. `닻` 같은 한 글자 실질 명사도 검색합니다. 문자열이 포함됐더라도 해당 어절을 분석했을 때 같은 명사가 아니면 점수를 주지 않습니다. 예를 들어 `범선의`의 일부를 `선의`로, `점검 토대`의 일부를 `검토`로 세지 않습니다. 원질의·임베딩은 유지하며 수치·부정·시점 조건을 질문이나 LLM 입력에서 삭제하지 않습니다. 새 복합 표현은 실제 제목/본문에 있을 때만 사용합니다.

용어 가중치는 현재 기준일의 검색 대상 조문 수 `N`과 해당 용어가 제목 또는 본문에 들어 있는 조문 수 `df`로 계산한 `ln(1 + (N + 0.5)/(df + 0.5))`에 길이 보정을 곱합니다. 같은 조에서 반복해도 한 번만 세며 긴 복합 명칭의 구성 명사는 중복 가중을 줄입니다. 명사 점수는 `0.6 × 일치 명사의 가중치 합/질문 명사 가중치 합 + 0.4 × 일치 명사 중 최대 가중치/질문 명사 중 최대 가중치`입니다. 따라서 긴 질문에서도 구체적인 설비명 하나의 정확한 일치가 충분히 반영됩니다. 이 점수는 확률이나 BM25 원점수가 아닙니다. 제목에만 있는 용어를 본문 일치로 취급하지 않으며, 명사 일치만으로 법적 적용을 확정하지 않고 기존 LLM 관련성 검토를 거칩니다.

명사 분석기는 프로세스 안에서 재사용하고 질문 분석 결과는 최대 512개, 일치 어절의 분석 결과는 최대 16,384개 캐시합니다. 조문 전체를 매 요청마다 형태소 분석하지 않습니다. 용어 빈도는 검색 요청의 적용 버전에서 계산하므로 삭제·개정·기준일 변경이 반영됩니다. 별도 AI 호출, 검색 메타데이터 생성, 원문 재수집이나 재임베딩은 필요 없습니다. 업데이트 후 `python -m pip install -r requirements.txt`로 패키지를 설치하고 서버를 재시작하세요. 첫 명사 검색에는 분석기 초기화 시간이 추가됩니다. 진단용 API 필드 `body_noun_score`, `title_noun_score`, `matched_body_nouns`, `matched_title_nouns`로 일치한 용어를 확인할 수 있습니다. `keyword_method`는 `noun_idf`이며 기존 ngram 점수 필드는 제거했습니다. 화면은 기존처럼 관련도 점수만 표시합니다.

법령명은 **원질의의 명사·복합명사와 저장된 법령명의 명사 사이의 일치율**로 별도 비교합니다. 공백·전각을 정규화하고 `기준`, `규정`, `지침` 같은 공통 명칭은 일치 가산에서 제외합니다. 실제 일치한 명사의 길이 합을 이름 길이로 나누며 이름의 명시된 수치·범위도 비교합니다. `어선` 질문은 `어선법`·`어선설비기준`, `레저기구` 질문은 `수상레저안전법`처럼 실제 대상 명사가 일치하면 점수를 받습니다. 반면 `일반선의`와 `범선의`에서 `선의` 두 글자가 겹쳐도 가산하지 않습니다. `총톤수 10톤 미만 소형어선`처럼 이름의 구체적 범위가 더 많이 일치하면 점수가 올라갑니다. 명사 일치가 있고 전체 이름을 명시하면 1이며, 같은 단위의 수치·범위가 명시적으로 다른 경우에는 이름 점수를 낮춥니다. rewrite가 새로 만들어 낸 이름으로는 가산하지 않습니다. 법령명은 검색 범위를 제한하는 필터가 아니므로 다른 법령·행정규칙의 관련 본문도 함께 후보가 됩니다. 기존 제목·본문 임베딩을 그대로 쓰며 법령명 비교 때문에 추가 임베딩 요청이나 재수집을 하지 않습니다.

후보 통과를 위한 가중합은 `본문 점수 = 0.65 × 본문 코사인 유사도 + 0.35 × 본문 명사 점수`, `근거 점수 = 0.80 × 본문 점수 + 0.20 × 조문 제목 명사 점수 + 0.10 × 법령명 일치율`이며 상한은 1입니다. 키워드 모드의 본문 점수는 본문 명사 점수입니다. 법령명이 안 맞는 기존 본문 후보의 점수를 낮추지 않고 이름이 맞는 후보에 최대 0.10을 더합니다. 본문 0.20 및 최종 임계치(웹 검색·채팅은 0.3 고정)를 통과해야 하므로 이름만 맞는 무관한 조문은 제외됩니다. 명시한 법령+조번호 직접 조회는 식별자 경로로 취급합니다. 최종 정렬에는 아래 RRF 가중치를 별도로 적용하며 검색 후에는 기존 LLM 관련성 검토를 거칩니다.

여기에 **독립 명사 검색 경로**를 병행합니다. 원질의 명사 중 실제 자료에 존재하고 가중치가 관측된 최고 가중치의 50% 이상이며 출현 조문 수가 `max(3, 전체 조문 수 × 0.1)` 이하인 용어를 핵심어로 봅니다. 그 핵심어가 **본문에 실제로 일치**할 때 `명사 경로 점수 = min(1, 0.8 × 본문 명사 점수 + 0.2 × 제목 명사 점수 + 0.1 × 법령명 점수)`를 계산합니다. 이 경로도 본문 명사 점수 0.20 및 임계치 0.3을 요구합니다. 기존 가중합 경로 또는 명사 경로 중 하나가 조건을 충족하면 후보가 되며 `admission_score`는 두 경로 점수 중 큰 값입니다. 따라서 약한 임베딩 때문에 정확히 일치한 전문 용어까지 35% 가중치로 희석되어 탈락하는 문제를 줄입니다. 제목/법령명만 일치하거나 rewrite에만 등장한 단어는 명사 보호 경로를 만들지 않습니다.

구형 `SEARCH_TITLE_WEIGHT`, `SEARCH_MIN_TITLE_SCORE`, `SEARCH_MIN_BODY_SCORE`는 새 채팅/API 검색에 사용하지 않습니다.

채팅 화면의 검색 설정 톱니바퀴와 옵션 화면은 제거했습니다. 웹 검색·채팅은 **RRF 순위 결합·근거 임계치 0.3**으로 고정합니다. 이전 화면이 요청에 보낸 `fusion`, `threshold`와 기존 `.env`/환경변수의 `SEARCH_FUSION`, `SEARCH_THRESHOLD`는 무시합니다. 최초 검색과 추가 검색에 같은 정책을 적용하며, LLM 검토 대상은 최대 15개입니다. 임계치 0.3은 아래 RRF 표시 점수가 아니라 위의 후보 통과 점수에 적용합니다. RRF는 임계치와 본문 조건을 통과한 후보에 대해 **필드 안의 검색 방식 결합 → 법령명·제목·본문 필드 결합** 두 단계로 계산합니다.

1. **제목 순위**: 원질의/rewrite별 제목 키워드·제목 임베딩 상위 50개 목록을 `Σ 1/(60+순위)`로 합칩니다. 각 목록의 합집합을 유지하며, 결합 후 다시 50개로 자르지 않습니다.
2. **본문 순위**: 같은 방식으로 본문 키워드·본문 임베딩 상위 50개 목록의 합집합을 결합합니다. 한 검색기에서 강하게 일치한 문서가 다른 검색기의 목록에 없다는 이유로 중간 단계에서 제거되지 않도록 합니다.
3. **법령명 순위**: 이름 일치율이 양수인 법령명을 점수순으로 상위 50개까지 정렬합니다. 같은 법령의 통과 조문에는 같은 이름 순위를 부여하여 조문 수나 ID 때문에 이름 점수가 달라지거나 다른 법령이 밀려나지 않게 합니다.
4. **최종 순위**: **본문 60%·조문 제목 30%·법령명 10%**로 `0.60/(60+본문 순위) + 0.30/(60+제목 순위) + 0.10/(60+법령명 순위)`를 계산합니다. 어느 필드에 없는 조문은 그 필드에서 0점을 받습니다. 키워드 모드도 세 필드를 분리하며 임베딩 목록만 사용하지 않습니다. 원질의에 명시된 법령+조번호 직접 조회는 제목·본문 순위의 상단에 배치하고, 이름 일치도 함께 반영합니다.

표시 점수는 `최종 RRF 원점수 / (1/61) × 100`입니다. 원질의/rewrite 개수가 최종 분모를 늘리지 않습니다. 세 필드 모두 1위면 100점이며 본문 단독 최대 60점, 제목 단독 최대 30점, 법령명 단독 최대 10점입니다. 법령명 일치가 없어도 제목·본문 두 필드로 최대 90점까지 받습니다. RRF는 원점수 차이를 반영하지 않으며 점수는 정확도·관련성의 확률이 아닙니다. 임계치는 이 표시 점수가 아니라 앞서 설명한 후보 통과 점수에 적용합니다. 핵심어 보호 후보의 RRF 점수를 임의로 높이지는 않습니다. **화면에는 RRF 점수 하나를 ‘관련도 점수’로 통일**하여 별도 줄의 파란색 굵은 숫자로 표시하고 그다음 줄에 시행일을 표시합니다. 필드별 내부 점수는 화면에 노출하지 않습니다. 연결 자료의 점수는 내부 문맥 예산에만 쓰며 화면에 표시하지 않습니다. 표시 대상 상하위 자료는 대신 ‘상하위 연결 근거’로 표시합니다.

웹의 `/api/search/compare`는 제거했습니다. 개발용 비교는 아래 로컬 CLI에서만 실행할 수 있습니다. CLI 비교 옵션은 웹 검색·채팅의 고정 정책에 영향을 주지 않으며 최종 LLM 답변도 생성하지 않습니다.

```powershell
.\.venv\Scripts\python.exe -m app.cli search "서울 전세보증금 보호" --rewrite "서울 소액임차인 우선변제 금액" --compare
```

채팅은 사용자 설정 없이 RRF와 임계치 0.3을 항상 사용합니다. 실제 질의와 정답 근거 묶음을 라벨링한 Recall@K/필수 근거 확보율 비교는 별도로 필요합니다. API는 `weighted_score`, `rrf_score`, `law_name_score`, `title_score`, `body_score`, `matched_units`를 제공합니다. `law_name_score`는 원질의의 이름 일치율이고 `title_score`는 가중합·임계치용 제목 키워드 점수이며, 제목 의미 점수는 `title_semantic_score`로 구분합니다. 최종 RRF 계산은 `rrf_field_ranks`의 법령명/제목/본문 순위(null은 해당 목록에 없음), `rrf_raw_score`, `rrf_max_score`로 확인할 수 있습니다. CLI 비교 결과의 `rrf_strategy=field_hierarchical`, `rrf_fields`, `rrf_constant`, `law_name_weight`, `law_name_method`도 계산 방식을 명시합니다. API의 `score`/`rrf_score`는 0~1이며 화면에서 100을 곱해 표시합니다.

설치 적용 시점을 묻는 질문에서도 설치 요건 조문은 부분 근거로 검토합니다. 조문 자체에 건조 연도가 없으면 부칙·적용례를 추가로 확인해야 하며 본문의 `<개정 날짜>`를 적용 연도로 추정하지 않습니다. 의장수처럼 계산·적용 대상을 정의하는 조문도 설비 수량 질문의 보조 근거가 될 수 있지만, 계산 조문만으로 종류·질량·수량표가 확보되었다고 판단하지 않습니다. LLM 관련성 검토에서는 법령명과 본문에 명시된 적용 대상·산정 대상을 질문과 비교합니다. 특수 대상의 규정을 일반 기준으로 대체하거나, 서로 다른 정원·인원 개념을 같은 것으로 취급하지 않도록 합니다. 명시된 대상이 충돌하는 경우와 세부 적용 조건이 미확인인 경우를 구분합니다.

### 실제 DB에서 검색 누락 단계 확인

수집이나 재임베딩 없이 아래 명령으로 자료 보유/기준일 적용 여부, 임계치, 필드별 순위, 15개 선정, LLM 제외 여부를 보고서에 기록합니다. `--chat`은 실제 채팅 흐름과 AI API 호출을 실행합니다. 빼면 원질의 검색만 진단하며 `--mode keyword`까지 지정하면 AI 호출 없이 실행합니다. 보고서 필터는 검색 범위 자체를 바꾸지 않습니다.

```powershell
.\.venv\Scripts\python.exe -m app.diagnose_search "총톤수 10톤 미만 소형어선의 단독경보형감지기는 몇 년도 이후 건조된 어선부터 설치해야 하는가?" --law "총톤수 10톤 미만 소형어선의 구조 및 설비기준" --article 제58조 --article 제59조 --chat --output detector_diagnostics.json
.\.venv\Scripts\python.exe -m app.diagnose_search "의장수별로 비치해야 하는 앵커의 크기와 수량은 어떻게 되는가?" --law 선박설비기준 --article 제57조 --chat --output anchor_diagnostics.json
```

`retrieval_rank`는 후보 보호 전 RRF 순위이며 `body_focus_score`, `matched_focus_nouns`는 원질의의 본문 핵심어 일치입니다. `admission_score`와 `noun_admission_score`는 임계치 통과 경로를 보여 줍니다. `stage`는 검색 단계, `chat_stage`는 실제 LLM 검토 후 상태입니다. `llm_rejected`는 관련성 검토 탈락, `visible_source`는 최종 출처 포함입니다. 진단 보고서에는 키·벡터·조문 전체 본문을 저장하지 않습니다. `--as-of 2026-10-22`로 과거 요청의 기준일을 재현할 수 있습니다.
